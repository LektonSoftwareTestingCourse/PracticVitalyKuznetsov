# Тестовый план СМП

> Документ 2 из 4. Отвечает на вопросы как, кем и когда выполняются проверки и по каким измеримым признакам работа завершена.

## 1. Область и подход

**Объект:** СМП целиком — 11 сервисов, PostgreSQL, RabbitMQ.

**Ядро:** Authorization и Card Management — полный набор техник тест-дизайна и модели с ограничениями. **Периферия:** Gateway, Switch, симуляторы, Bin Lookup, Notification Service, Transaction Logger, Dashboard — чек-листы и классы верхнего уровня.

**Порядок выполнения проверок:** сначала автоматизируемые уровни (юнит → API), затем сквозные сценарии, затем нагрузочный smoke и ручные чек-листы.

## 2. Критерии входа

- `docker compose up -d` поднимает все сервисы, `docker compose ps` — все контейнеры в состоянии `Up (healthy)`;
- health-check всех сервисов отвечают 200, включая `/actuator/health` для Bin Lookup и Notification Service;
- `scripts/smoke-test.sh` завершается `🎉 ALL CHECKS PASSED`;
- генератор создал не менее 20 карт (`POST /api/cards/generate`);
- ТЗ-04 и ТЗ-05 зафиксированы и не изменялись после начала проектирования тестов;
- тестовые данные синтетические, реальные PAN не используются.

## 3. Критерии выхода

- нет открытых дефектов критического и высокого уровня;
- покрытие допустимых пар в попарных наборах ядра — 100 % (294 из 294 для Authorization, 151 из 151 для Card Management);
- в `test-design.md` есть разделы «классы эквивалентности», «граничные значения», «попарное тестирование», «тест-кейсы»;
- каждый тест-кейс содержит идентификатор и ссылку на требование;
- для каждой границы заданы три точки: ON, OFF ниже, OFF выше;
- модель PICT содержит не менее шести параметров и хотя бы одно ограничение, набор `cases.txt` не пуст;
- пройден лист само-приёмки из задания (7 пунктов).

| Уровень | Критерий готовности |
|---|---|
| Юнит | покрытие ветвей бизнес-логики ≥ 80 %, `mvn test` зелёный локально и в CI |
| API | 100 % эндпоинтов целевых сервисов покрыты позитивными и негативными проверками |
| E2E | покупка, отказ и возврат проходят стабильно, нет необъяснённых flaky-тестов |
| Нагрузочный smoke | ≥ 500 транзакций, собраны p50/p95/p99, throughput и error rate |
| Чек-листы | дымовое тестирование и критический путь пройдены, все пункты отмечены |

## 4. Приостановка и возобновление

**Приостановка**, если: более одного сервиса не становится `healthy` за 15 минут после старта; найден блокирующий дефект (транзакция не доходит до Logger, списание без авторизации, двойное списание); открытый вопрос к ТЗ блокирует более 20 % кейсов уровня; в `main` вносятся изменения в код ядра во время заморозки.

**Возобновление**, когда: окружение восстановлено и дымовой чек-лист пройден; блокирующий дефект закрыт или согласован обход с фиксацией в отчёте; получен ответ на блокирующий вопрос и затронутые кейсы обновлены.

## 7. Риски

| Риск | Мера снижения |
|---|---|
| модель без ограничений порождает нереализуемые сочетания | обязательные ограничения и проверка генератором, что все строки выполнимы |
| покрытие пар принимают за гарантию полноты | раздел «Ограничения техники» и ручные критичные сочетания |
| документация составлена на один сервис | стратегия и план строятся на всю систему, ядро и периферия разделены |
| невалидные значения смешаны в одном кейсе | правило «один невалидный класс — один кейс», проверяется на самопроверке |
| ожидаемые результаты выдуманы там, где ТЗ молчит | открытые вопросы ОВ-1…ОВ-8 вынесены в `test-design.md` |
| неатомарность «проверить баланс → зарезервировать» даёт flaky-тесты | `TC-CMS-BV-09`, изоляция данных между прогонами |
| PICT недоступен в окружении | резервный `pict/generate.py`, наборы закоммичены |
