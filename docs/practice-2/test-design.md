# Test-design ядра СМП: Authorization и Card Management

> Документ 3 из 4. Техники: классы эквивалентности, граничные значения, попарное тестирование.

## Шаги и наблюдения

Кейсы разделов 1 и 2 записаны кодами, чтобы не повторять одни и те же действия в каждой строке.

| Код | Действие |
|---|---|
| `З1` | подготовить карту с нужными статусом, лимитами, балансом и `expiryDate` |
| `З2` | взять PAN, отсутствующий в CMS |
| `З3` | засеять `limit_usage` под нужное значение `daily_usage` |
| `З4` / `З5` | остановить Card Management / Bin Lookup |
| `З6` | взять PAN, отсутствующий в БД |
| `З7` / `З8` / `З9` | подготовить карту в статусе ACTIVE / BLOCKED / DELETED |
| `П1` | `POST /api/internal/authorize` |
| `П2` | `PATCH /api/cards/{pan}` |
| `П3` | `DELETE /api/cards/{pan}` |
| `П4` | `POST /api/cards` или `POST /api/cards/generate` |
| `П5` | `GET /api/cards/{pan}` или список `GET /api/cards` с фильтром |
| `П6` | `POST /api/cards/{pan}/reserve` |
| `О1` | сверить `responseCode` и `declineReason` |
| `О2` | при APPROVED: баланс уменьшен на сумму, RRN — 12 цифр, authCode — 6 символов |
| `О3` | при APPROVED: запись в `limit_usage` обновлена |
| `О4` | сверить HTTP-код и тело ответа |
| `О5` | проверить `outbox_event` и публикацию в `smp.card-events` |

Общие предусловия: СМП развёрнута, сервисы healthy, карты сгенерированы (≥ 20).

## 1. Классы эквивалентности

На каждый класс — минимум один представитель. Позитивные и негативные классы выделяются раздельно; один невалидный класс — один тест-кейс, невалидные значения не смешиваются.

## 2. Граничные значения

На каждую границу — три точки: **ON** — ровно на границе, **OFF ниже** и **OFF выше** — на единицу за ней. Суммы — в копейках.

Базовые данные Authorization: `dailyLimit = 10 000 000`, `monthlyLimit = 300 000 000`, `availableBalance = 20 000 000`, `daily_amount = monthly_amount = 0`.

### 3.3 Ограничения техники и добавленные вручную сочетания

Попарное покрытие не гарантирует проверку взаимодействий трёх и более параметров. Критичные сочетания добавлены в набор вручную и перечислены ниже.

**Authorization:** сумма ровно на границе баланса (ON) при прочих валидных условиях; граница MMYY «текущий месяц» в связке с полным happy-path; все лимиты валидны, но баланса не хватает → `51`; недоступный Bin Lookup при полном happy-path (проверка fallback целиком).

**Card Management:** happy-path частичного обновления; обновление при недоступном брокере (outbox → FAILED); `PATCH` карты в статусе BLOCKED; мягкое удаление активной карты; чтение существующей активной карты.

Прочие ограничения техники:

- границы проверяются не парой, а тройкой ON / OFF, поэтому вынесены в раздел 2 и в сценарные кейсы `TC-AUTH-BV-09…10`, `TC-CMS-BV-09`;
- модель описывает состояние на момент одного запроса; последовательности транзакций (накопление лимита, переход через месяц) в попарной модели не выражаются;
- `amount_vs_*` — это отношения, а не абсолютные суммы: при автоматизации для каждой строки подбираются конкретная сумма и предварительно засеянные записи `limit_usage`, при которых все отношения строки выполняются одновременно.

### 3.4 Воспроизведение наборов

```bash
# канонический путь, Microsoft PICT
pict model.txt > cases.txt
pict card-management/model.txt > card-management/cases.txt

# резервный путь без внешних зависимостей
python generate.py model.txt cases.txt --extra critical-combinations.txt
python generate.py card-management/model.txt card-management/cases.txt --extra card-management/critical-combinations.txt
```

Генератор печатает объём перебора, число допустимых пар и покрытие, строки из `critical-combinations.txt` проверяет на совместимость с ограничениями модели.

## 5. Открытые вопросы к ТЗ

Где ТЗ не задаёт ожидаемый результат, он не выдумывается: вопрос фиксируется здесь, тест-кейс ссылается на его номер.

| № | Вопрос | Где влияет |
|---|---|---|
| ОВ-1 | Валидируется ли PAN в пути запроса (`GET`, `PATCH`, `DELETE`)? Проверка Луна описана в ТЗ как бонусная для создания карты. Невалидный PAN — это 404 или 400? | `TC-CMS-BV-01`, `TC-CMS-PW-08…13,15,17` |
| ОВ-2 | Что важнее при невалидном поле в теле `PATCH` — 400 без применения изменений или частичное применение? Что проверяется первым: идентификация карты или валидация тела? | `TC-CMS-PW-10,16` |
| ОВ-3 | Отличается ли `responseCode` при превышении месячного лимита от дневного? В ТЗ указано «аналогично», отдельный код не приведён. | `TC-AUTH-EQ-12`, `TC-AUTH-BV-02` |
| ОВ-4 | Допустимы ли нулевые и отрицательные `dailyLimit`, `monthlyLimit` и `initialBalance` при создании карты и в `PATCH`? | `TC-CMS-EQ-03,04`, `TC-CMS-BV-03` |
| ОВ-5 | Как ведёт себя `POST /api/cards/{pan}/reserve` при `amount > availableBalance`? В штатном потоке вызов идёт после проверки баланса, но проверка и резервирование неатомарны. | `TC-CMS-EQ-18`, `TC-CMS-BV-09` |
| ОВ-6 | Есть ли ограничения на `count` и `bins` в `POST /api/cards/generate`: допустим ли `count = 0`, есть ли верхняя граница? | `TC-CMS-EQ-20`, `TC-CMS-BV-07` |
| ОВ-7 | Допустима ли авторизация с суммой меньше или равной нулю? В ТЗ ограничение не задано. | `TC-AUTH-BV-08` |
| ОВ-8 | Должен ли `expiryDate` участвовать в фильтрации `GET /api/cards`: переход ACTIVE → EXPIRED выполняется по дате автоматически или только явным `PATCH`? | `TC-AUTH-EQ-06`, `TC-CMS-EQ-10` |
